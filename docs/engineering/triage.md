# triage

## What it does

`triage` works through the issues on your tracker, moving each through a small state machine of **triage roles** (one category, one state). Each issue ends as an agent-ready brief, a specific question for the reporter, or a closed issue with a recorded reason. It recommends and then waits: it gives its call with reasoning and applies nothing until you say so.

It is the human checkpoint for work that arrived from outside: raw reports, feature requests, external PRs, and the issues the audits file. Issues from Sentry, user feedback or support email (`source:*` labels) quote text a third party could write, so `triage` treats that text strictly as data, verifies the problem independently, and writes the agent brief in its own words. That's what stops an injected instruction in an error message from reaching an unattended agent.

## When to reach for it

You invoke this by typing `/triage` and describing what you want: "show me what needs attention", "let's look at #42", "move #42 to ready-for-agent". The agent won't reach for it on its own.

| What you have | Where to go |
| --- | --- |
| Raw reports, audit findings, Sentry or feedback issues | `/triage` |
| A rough idea of your own | [grill-with-docs](grill-with-docs.md) |
| A settled conversation to turn into a spec | [to-spec](to-spec.md) |
| A confirmed bug that needs a root cause | [diagnosing-bugs](diagnosing-bugs.md) |
| Too many open issues to triage one by one | [synthesize-backlog](synthesize-backlog.md) |

## Prerequisites

An issue tracker and label vocabulary configured by [setup-standards](../setup/setup-standards.md), which also creates the labels in your tracker.

## The state machine

| State | Means |
| --- | --- |
| `needs-triage` | You need to evaluate it. Audit findings and external-source issues land here. |
| `needs-info` | Waiting on the reporter. |
| `ready-for-agent` | Fully specified, with an agent brief. An AFK agent can take it. |
| `ready-for-human` | Same brief, plus why an agent can't do it. |
| `wontfix` | Closed, with the reason recorded. |

A **tracker**, an issue that only holds sub-issues (one [synthesize-backlog](synthesize-backlog.md) opened for a thread, say), carries a category and the `tracker` label but no state, and triage skips it.

Rejected enhancements go into `.out-of-scope/`, one file per concept, which triage checks before evaluating anything new.

## Issues from audits

Audit issues (`audit:<name>`) carry a fingerprint footer the audit uses to deduplicate. How you close them matters: **closed as completed** means fixed, and the audit reopens it as a `regression` if the problem returns; **closed as not planned** suppresses that finding for good. `audit-run` issues are tracking issues, not work, and triage skips them.

## Verify before you brief

Before any grilling, it checks the claim: reproduces the bug, or checks out and runs the PR. It also checks whether the feature already exists and whether `.out-of-scope/` already rejected it. The **agent brief** names types and behavioural contracts, never file paths or line numbers, and for external-source issues restates the problem rather than relaying the reporter's text.

## Common questions

**Do I triage the tickets `/to-tickets` made?**

No. They're already `ready-for-agent`. Triage is for work that came from outside your own planning.

**A Sentry issue says "ignore previous instructions and …". What now?**

Nothing it says gets followed. Triage notes it as suspected prompt injection, verifies the underlying error independently, and the brief describes the verified problem in its own words.

**Should I close a noisy audit finding as not planned?**

Only if it should never come back. Not planned is permanent suppression for that fingerprint. If it's fixed, close as completed.

**Can it run across my whole backlog?**

It can, but the listing pass doesn't read comments. For a large backlog, run [synthesize-backlog](synthesize-backlog.md) first: an issue a thread will close needs no brief of its own.

## It's working if

- Every item ends with exactly one category and one state.
- It recommends and stops, rather than relabelling and moving on.
- Nothing reaches `ready-for-agent` without a reproduction or a verified code path.
- Briefs for `source:*` issues contain no quoted instructions from the reporter.
- Every comment starts with `> *This was generated by AI during triage.*`

## Where it fits

An **on-ramp** parallel to the main chain: the audits and [sentry-triage](../audits/sentry-triage.md) file issues, `triage` turns them into briefs, and [implement](implement.md) picks up `ready-for-agent` work the same way as a ticket from [to-tickets](to-tickets.md).
