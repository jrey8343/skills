# Fold

Turn an earlier run's threads into **thread trackers**: issues that hold a thread's members as sub-issues. It runs in any session, any day after the run, from the run that `assemble.mjs keep` saved. `<run>` below is that kept run, and `<skill>`, `<repo>` and `<owner>/<name>` are as in SKILL.md.

1. **Find the run.** Use the path the user gave. With none, list `<state>/synthesize-backlog/<owner>-<name>/`, where `<state>` is `$XDG_STATE_HOME`, else `~/.local/state` (`%LOCALAPPDATA%` on Windows), and confirm the newest with the user. Done when `assemble.mjs summary <run>` prints a first line naming this repo; stop if it names another.

2. **Refresh.** Issues change between sessions, so bring the run up to date before anything is written. With the run's area (the summary's first line names it, if there was one), use the same filter in the list and the count, as in SKILL.md step 1:

   ```sh
   gh repo view --json issues --jq .issues.totalCount
   gh issue list --state open --limit 2000 --json number --jq '[.[].number]' > <run>/open-now.json
   gh api graphql --paginate -f owner=<owner> -f name=<name> -F query=@<skill>/scripts/links.graphql --jq '.data.repository.issues.nodes[]' > <run>/links.jsonl
   node <skill>/scripts/assemble.mjs refresh <run> --open-count <count> --date <YYYY-MM-DD>
   node <skill>/scripts/render-report.mjs <run>/synthesis.json <run>/report.html
   node <skill>/scripts/assemble.mjs summary <run>
   ```

   Done when `refresh` exits 0. Issues closed since the run are now struck through, and members that gained a parent are listed instead of attached. The code is not re-checked: tell the user how far the run's code is behind (`git -C <repo> rev-list --count <code sha>..origin/<default>`), and treat a thread whose members have mostly closed as likely done.

3. **Pick.** Open the report for the user and give its path. From the summary, give the Strong threads in a line each and the triage plan, and ask which threads to fold. A thread the summary marks `folded as #N` already has a thread tracker from an earlier session: leave it unless the user asks to extend #N.

4. **Labels.** Take the tracker label from the Trackers section of `docs/agents/triage-labels.md`. A repo set up before that section existed has none: propose `tracker` (and running `/setup-standards` again), and ask before creating it. Check that it and the `enhancement` category role's label exist with `gh label list`.

5. **Plan each thread.** Run `assemble.mjs tracker <run> <id> --picked <every picked id, comma-separated>`. It writes the thread tracker's body file and prints:
   - `title_shell`, the title already quoted for the shell;
   - `attach`, the members to attach;
   - `listed`, the members it only lists, each with its reason: an existing tracker, closed since the snapshot, owned by another picked thread, already under a parent, or over GitHub's 100 sub-issue limit;
   - `existing_trackers` among the thread's existing proposals, and `folded_as` when an earlier session folded it;
   - a `warning` when fewer than three members are left to attach.

   It refuses a thread with nothing to attach: open no thread tracker for it, and tell the user which picked threads hold its members. When `warning` is set, ask whether to open the thread tracker anyway.

6. **Create or extend.** Write each thread tracker's body, and each comment that extends a tracker, from the body file: it opens with the AI disclaimer and has its @mentions neutralised. Start any other comment with `> *This was generated by AI during backlog synthesis.*`.
   - When `existing_trackers` is not empty, ask whether to extend one or open a new thread tracker. To extend #N, attach the members in `attach` to #N and post the body file on #N as a comment.
   - Otherwise run `gh issue create --title <title_shell> --label <tracker label> --label <category label> --body-file <body_path>`, pasting `title_shell` exactly as printed. Then attach each member in `attach` as a sub-issue, the way the issue tracker doc says. When GitHub refuses one because it has gained a parent since the refresh, leave it under that parent, never replacing it, and name it in a comment on the thread tracker.
   - Close nothing: a member closes when its fix ships.

   After each, record it: `assemble.mjs folded <run> <id> <tracker number>`, so a later fold session knows.

7. **Hold reversed briefs.** List the ready-for-agent briefs the folded threads would reverse (the triage plan names them), and ask once whether to hold them. For each one held, comment with what the thread changes in it, and move it to the needs-triage role's label from `docs/agents/triage-labels.md`.

Done when every picked thread has a thread tracker with its members attached or listed, or was refused for having none to attach, every one is recorded with `folded`, and the user has answered about the briefs. End by naming each thread tracker's entry point (`/implement`, `/to-spec` or `/wayfinder`, which the user starts by typing it), and send the issues no thread covers to `/triage`.
